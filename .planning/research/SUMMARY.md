# Project Research Summary

**Project:** FreeShow
**Domain:** Design-system adoption (shadcn-svelte + Tailwind v4) inside a brownfield Electron + Svelte desktop application — starting with the Settings surface
**Researched:** 2026-10-17
**Confidence:** HIGH

> **Scope:** Milestone 1 only — design-system foundation + Settings revamp. Milestone 2 (AI: transcription, auto-scripture model selection, AI layout designer) is deliberately excluded from this synthesis.

## Executive Summary

This is not a greenfield build and it is not a reskin. FreeShow is a live-service presentation app whose Core Value is "the show must not fail," and the milestone changes the *build platform* (Svelte 3→5, Vite→7, TypeScript→5.9), the *styling engine* (Tailwind v4), and the *control layer* (shadcn-svelte + Bits UI) of an app whose renderer bundle is shared, byte for byte, with every live projector output window. The research converges hard on one path — **Svelte 5 in legacy mode, Tailwind v4 with Preflight omitted, shadcn-svelte 1.7 / bits-ui 2.19, Vite 7 (not 8)** — and the reason is not aesthetics: Svelte 5's legacy mode means all 464 existing components keep working unchanged (the only mechanical code change is **six** `new App()` → `mount()` lines), while the alternative shadcn-svelte 0.14.3 line is a frozen dead end whose registry is archived and whose components pin `bits-ui@0.22.0`. Path B buys one deferred migration now and pays three chained migrations later, the last two of which no upgrade tool has ever seen FreeShow's bespoke Vite config.

The decisive discovery across all four documents is that **the hard constraint is not the framework upgrade — it is the shared stylesheet.** Main, output/projector, export, and offscreen-capture windows all load the same `public/index.html` and therefore the same `bundle.css`. There is no per-window CSS, no separate output entry point, and no tree-shaking of Settings code out of the output window. Any global CSS the design system introduces — Preflight, a `:root` `@theme` token block, a `.dark` toggle — is compiled into that shared bundle and applies **inside every live projector output**. The no-leak requirement therefore cannot be satisfied by file separation or build targets; it is satisfied by three deliberate omissions that must all hold: (1) never import Preflight, (2) never write new tokens or a dark-mode class to `:root`/`documentElement`, (3) scope the entire new system — variables, base styles, and Bits UI portals — to a marked Settings subtree (`[data-ds="v2"]`).

The second discovery is that **FreeShow is already token-based.** `updateThemeValues()` (`src/frontend/utils/updateSettings.ts:253`) writes a fixed set of custom properties to `document.documentElement` from the active user theme, and `public/global.css` holds the same names as defaults; `var(--…)` is referenced 1,318 times. The work is therefore **namespace reconciliation, not token introduction** — and the collision is severe: FreeShow's `--primary` is a dark *surface* (`#242832`) while shadcn's `--primary` is the *brand/CTA* colour, and FreeShow's `--secondary` is the hot-pink brand accent while shadcn's is a muted neutral. Repointing them would silently recolour ~600 `var(--primary*)`/`var(--secondary)` reads across 351 files, every entry in `defaultThemes.ts`, and the output windows simultaneously. The resolution is not to rename and not to repoint, but to **bridge**: keep legacy names frozen, add a new semantic namespace, and use Tailwind's `@theme inline` to map shadcn's *utility class names* (`bg-primary`) onto those new variables. Vendored shadcn components then compile unmodified and resolve to FreeShow colours, while `var(--primary)` everywhere else still means what it always meant.

The two highest risks are different in kind and must not be confused. **Phase 1 (the toolchain gate) carries the highest risk of going wrong** — Svelte 5 cannot be installed alone; Vite, the Svelte plugin, TypeScript, `svelte-check`, ESLint's Svelte plugin, the tsconfig base, and Vitest must all move together, in a repo with 12 test files for ~1,013 sources and non-blocking type checks. **The shared-stylesheet constraint carries the highest severity if it goes wrong** — a Preflight reset on a lyrics/scripture/overlay renderer is an on-air regression, not a rendering bug. Mitigation for the first is sequencing discipline (one self-contained phase, legacy syntax preserved, release smoke checklist, no `runes: true` project-wide); mitigation for the second is a mechanical gate (omit Preflight, don't touch `global.css`/`:root`, scope everything to `[data-ds="v2"]`, and assert an output-window pixel-diff at 1920×1080 before and after every CSS-touching phase).

## Key Findings

### Recommended Stack

**Path A — Svelte `5.57.2`, Tailwind `4.3.3`, shadcn-svelte `1.7.0`, bits-ui `2.19.5`, Vite `7.3.7`, TypeScript `5.9.3`.** This is close to dispositive rather than a preference. Svelte 5's legacy mode is auto-selected for any component not using runes, so every existing pattern in the repo (`export let` ×317, `$:` ×419, `on:` ×404, `<slot>` ×37, `createEventDispatcher` ×77, `bind:` ×170) keeps compiling; the repo's Svelte API surface is unusually clean (zero `svelte/internal`, `SvelteComponentTyped`, `$$restProps`, `.=$set`, or `<svelte:options>`), so the breaking-change list barely engages. The Svelte 4 shadcn line is frozen by construction: its CLI hardcodes its registry to `svelte-4.shadcn-svelte.com` and pins `bits-ui@0.22.0` exactly, and there is no forward maintenance.

**Vite 7, not Vite 8.** Vite 8 replaced Rollup with Rolldown. FreeShow's renderer build is a non-standard single **IIFE `build.lib` bundle** that is *also* loaded by every output window; Vite 7 keeps Rollup 4 (the same bundler the repo already uses for its server builds). Moving to Rolldown belongs in a later, isolated upgrade once the IIFE output has been validated against it.

**Core technologies:**
- **`svelte@5.57.2`** — compiler/framework; legacy mode makes the upgrade a tooling change, not a 400-file rewrite
- **`vite@7.3.7` + `@sveltejs/vite-plugin-svelte@6.2.4`** — the highest pairing still on Rollup-based Vite; satisfies Tailwind v4's `vite >=5.2` floor
- **`tailwindcss@4.3.3` + `@tailwindcss/vite@4.3.3`** — the only version the current shadcn-svelte line supports; `@tailwindcss/postcss` and `postcss.config.js` are explicitly removed by shadcn's own v4 guide
- **`shadcn-svelte@1.7.0`** (devDependency, CLI only, zero runtime footprint) + **`bits-ui@2.19.5`** (the WAI-ARIA layer that *is* the accessibility strategy)
- **`typescript@5.9.3`** — forced by an intersection of four peer ranges; **`7.0.2` (`latest`) is out of band for the Svelte toolchain and must not be adopted**
- Support: `clsx` + `tailwind-merge` (`cn()`), `tailwind-variants@3.3.1`, `tw-animate-css@1.4.0`, `@lucide/svelte@1.59.0`
- Tooling: `svelte-check@4.7.7`, `vitest@4.1.12`, `prettier-plugin-svelte@4.1.1`, `eslint-plugin-svelte@3.23.1` + `svelte-eslint-parser@1.9.0` + `typescript-eslint@8.71.2`

**Non-negotiables that are easy to miss:** every new package goes in **`devDependencies`** (the renderer libs already follow this convention and `electron-builder` packages `dependencies`); `eslint-plugin-svelte3` is Svelte-3-only and must be replaced; `svelte-preprocess` must be dropped in favour of the existing `vitePreprocess()`; and the Tailwind CSS must be **imported from `src/frontend/main.ts`**, not `<link>`-ed, because in production the build is `build.lib` with `root: "."` and `public/index.html` is never a build input.

### Expected Features

This is a revamp: there are no new user-facing capabilities. The "features" are **deliverables and qualities** measured against three stated goals — visual consistency, clearer IA/flows, and accessibility/responsiveness. Because all three are in scope, several items a styling-only revamp would skip are genuinely P1 here. That distinction — reskin vs. revamp — is the single most important scoping judgement in this file.

**Must have (table stakes, all P1):**
- **Token layer reconciled with the existing Theme feature** — extend the ~15-variable seed to semantic roles; must not bypass `Theme.svelte`/`defaultThemes.ts` (highest-leverage item)
- **One shared control primitive set replacing the two parallel control layers** — `components/input/` (9 wrappers) and `components/inputs/` (32 Material components); rebuild the *wrappers* on primitives so all ~21 tabs inherit the change without per-tab rewrites
- **Accessibility fundamentals:** keyboard operability (2.1.1/2.1.2), visible focus (2.4.7, target 2.4.13 — 15 components currently set `outline: none`), focus not obscured by the sticky header (2.4.11), accessible name/role/state (4.1.2/1.3.1/3.3.2), target size ≥24×24 (2.5.8), contrast 4.5:1 / 3:1 (1.4.3/1.4.11)
- **Accessible Settings navigation** — `SettingsTabs.svelte` today is styled `<button>`s with no tablist/tab semantics, no `aria-selected`, and ArrowUp/Down only
- **IA consolidation** — reduce/regroup the 10 top-level tabs, remove the hidden "global output options" toggle that swaps the whole panel, adopt one documented sub-tab pattern (max 1 level)
- **Reflow + 200% text resize** (1.4.10/1.4.4); **explicit async/empty/error states** + destructive-action guards; **i18n preserved** (all strings via `T`/`translateText`)
- **Accessibility is testable, not asserted** — axe-core in the existing Vitest/Playwright harness; re-enable the Svelte a11y lint currently switched off (`config/linting/eslint.svelte.js:42`, `vite.config.mjs:13-17` `onwarn`)
- **Regression/parity safety** — no change to the store/IPC contract or the output path

**Should have (differentiators, v1.x):**
- **Settings search / jump-to-setting (Cmd/Ctrl+K)** — the #1 settings complaint; **requires** IA consolidation first, and must filter by profile permissions or it leaks restricted capabilities
- **Deep links into a specific setting** — reuses the existing `settingsTab` store
- **Per-setting reset + modified-from-default indicator** — generalizes the existing `defaultValue` dot
- **One consistent "Advanced" progressive-disclosure pattern**; **inline validation** for Connection/API/Files; **live preview panel** (read-only, off the critical output path); **non-drag reorder alternative**; **reduced-motion / `forced-colors`**
- **Component gallery / design-system page** — the "prove the layer is extensible" deliverable

**Defer (v2+):** undo/redo for Settings changes; cross-surface design system (main shell, stage/show editor — later milestones by design); mobile-web remote parity; Frontend TypeScript `strict` burn-down (~2,733 `any` uses — its own effort, and explicitly *not* part of this milestone).

**Anti-features (do not build):** big-bang migration of all 464 components; a visual reskin with no IA change; **a second theming system alongside `defaultThemes.ts`**; a global Apply/Save button (fights the app's immediate-apply model); nesting tabs deeper than one sub-level; modals for simple settings; **bespoke SVGs/CSS instead of shadcn primitives**; drag-only reordering (violates 2.5.7); icon-only buttons without accessible names; search that surfaces permission-gated or destructive settings; per-tab one-off fixes; and turning on TS `strict` as part of the UI milestone.

### Architecture Approach

The architecture is a **strangler-fig migration with an explicit token bridge**, not a refactor. Four components carry it: (1) a **token bridge** — `design/tokens.ts` `resolveThemeTokens(theme)` is a pure, framework-free function returning `{ legacy, semantic }` maps, derived from the one authoritative `$themes[$theme]` object; (2) a **token applier** — `design/applyTheme.ts`, invoked by the existing `updateThemeValues()` choke point so all 8 call sites (including undo/redo via `historyHelpers.ts` and theme switching via the context menu) are wired for free; (3) a **design stylesheet** — Tailwind's `theme` + `utilities` layers only, **no Preflight**, plus `@custom-variant dark` and an `@theme inline` block mapping shadcn utilities onto the new semantic variables; (4) a **primitive layer** — `src/frontend/components/ui/**`, vendored from the shadcn-svelte CLI and owned by the repo.

**Major components:**
1. **Token source** (`defaultThemes.ts`, THEMES store, `Themes` type) — unchanged; remains the single source of truth. `colors` is already an open `{[key:string]: string|null}` index, so new semantic roles are backward-compatible, and `border.radius` already exists unused — the radius plumbing was started and abandoned
2. **Token bridge** (`design/tokens.ts`, `design/roles.ts`) — derives every semantic role the theme doesn't define, allows per-theme overrides, reuses the existing `getContrast` helper for `*-foreground` pairs. Pure TS, unit-testable with the existing Vitest, **not blocked by the toolchain upgrade**
3. **Token applier** (`design/applyTheme.ts`) — writes to the DOM; the ~10-line body of `updateThemeValues` delegates here
4. **Primitives** (`components/ui/**`) — shadcn-svelte: button, input, label, select, switch, checkbox, radio-group, tabs, separator, scroll-area, dialog/popover/tooltip, collapsible
5. **Migration boundary** — `data-ds="v2"` on migrated containers, giving a grep-able review marker and the scope for every new variable and base style

**The mandated coexistence rules — "swap, don't restyle":** legacy Svelte scoped CSS compiles to `.class.svelte-hash` (specificity 0,1,1) which **beats** a Tailwind utility (0,1,0), and the repo carries 1,956 inline `style=` attributes and 489 `:global(...)` rules, which beat both. Adding utilities to a legacy element therefore produces specificity wars, dead CSS, and `!important` escalation. So: (1) additive tokens only, legacy names frozen; (2) no Preflight, no edits to `global.css`, all new CSS in its own file; (3) a migrated control is a `ui/` primitive and the legacy markup+styles are deleted in the same commit — no hybrids; (4) utilities scoped under `[data-ds="v2"]`; (5) per-file, per-commit migration so `main` stays shippable. Reversibility is a three-step ladder, with the strongest rung being "delete the CSS import and revert a ~10-line function body" — **zero data migration, because themes are never rewritten**.

### Critical Pitfalls

1. **The shared bundle means global CSS reaches the live output windows.** The same `bundle.css` is loaded by main, output/projector, export, and offscreen-capture windows; `loadWindowContent(window, "output")` loads the same `public/index.html`. Preflight resets margins, heading sizes, image display, and border defaults — on a lyrics/scripture renderer that is an on-air regression. *Avoid:* omit Preflight entirely, import only `theme`+`utilities` layers, add a `[data-ds="v2"]`-scoped base block, never write DS tokens or `.dark` to `:root`, keep Bits UI portal targets inside the Settings subtree, and gate every CSS-touching phase with an output-window screenshot diff at 1920×1080.
2. **shadcn's token names silently collide with the shipped theme system.** `--primary`, `--secondary`, `--accent` collide by name with inverted meaning. Adopting shadcn's scaffold verbatim either repaints the app with shadcn's neutrals the moment a theme loads, or paints shadcn surfaces in FreeShow's brand colours in the wrong roles (a "secondary" button in hot pink). It also breaks the derived contrast logic in `App.svelte:53-55` and every `var(--secondary)` usage in context menus, trackers, stage tools, and the audio-routing graph. *Avoid:* never repoint legacy names; write a token contract document (role / source / user-editable) before any component is vendored; add an assertion that no shadcn surface picks up `#242832` and that `#F0008C` appears only where intended.
3. **"Upgrade Svelte" is a coupled platform migration, not a dependency bump.** `vite-plugin-svelte@2.5.3` peers Svelte ≤4 and Vite 4; `svelte-check@2.10.3` and `eslint-plugin-svelte3@4` are Svelte-3-only; `typescript@4.9.5` is below every new peer; `@tsconfig/svelte@2` predates the `verbatimModuleSyntax` requirement of the new TS preprocessor; `svelte-preprocess` is replaced by `vitePreprocess()`; `vitest@2` is pinned to the Vite 4 range. *Avoid:* do it as one self-contained phase with **zero syntax migration**, sequence Vite+plugin first, then Svelte, then TS/check/lint, validate on all three OSes, and stand up a release smoke checklist *before* starting (there is no automated safety net).
4. **Svelte 5's event/prop model breaks at component boundaries — which is where this codebase lives.** 259 files declare `export let`, 308 use `on:click`, 65 use `createEventDispatcher`, 138 use `bind:`, 26 use `<slot>`; `on:click|preventDefault` has no `onclick` equivalent; within a file you cannot mix `$:` with `$derived` or `export let` with `$props()`. The failures are silent (a control that renders but never propagates its value), not compile errors. *Avoid:* migrate bottom-up; pick one event convention for new code (`onclick`) and enforce it with a lint rule; prefer callback props across legacy↔runes boundaries; **write the input-propagation test before converting `Input.svelte`**; never enable project-wide `runes: true`.
5. **The production build pipeline is bespoke and brittle.** Vite library mode + IIFE, then `scripts/postBuild.js` does exact-string replacement of the entry script in `public/index.html` and **throws `"Dev script path changed!"`** if the string is absent; `cleanBuilds.js` mirrors that literal; Terser post-minifies with `mangle.toplevel` and calls `process.abort()` on failure; `assetFileNames` renames CSS to `bundle.css`. If Tailwind's CSS pipeline changes the emitted asset name, `index.html` references a missing stylesheet — **an unstyled app in production only**. *Avoid:* add a build-output assertion (referenced files exist, `bundle.css` non-empty and contains a known class, exactly one CSS file emitted) and validate the CSS emission path with a trivial import before writing any UI.
6. **Tailwind v4's native engine (`@tailwindcss/oxide`) interacts badly with `npm ci`, CI matrices, and emulated cross-builds.** Silent generation of partial CSS under QEMU, optional platform binaries failing to install (the class of bug already documented in `.gitignore:1-3` for `@rollup/rollup-*`), and build-time natives getting tangled in `electron-builder install-app-deps`. *Avoid:* keep Tailwind and Oxide strictly in `devDependencies`; pin the lockfile; never use `--omit=optional`; build CSS on a native runner for arm64; assert a known class exists in the built CSS.
7. **Global `user-select: none`, transparent frameless always-on-top windows, and `backgroundThrottling: false` fight shadcn primitives.** Inputs need `user-select: text`; the global `outline-offset: -4px` interacts with `--ring`/`--ring-offset`; portals mounted to `document.body` can render inside a transparent output window; floating-ui/`ResizeObserver`/rAF keep running unfocused and compete with the rAF-driven effect renderer; the app already has an "optimized mode" that strips `backdrop-filter`. *Avoid:* an explicit `.ds-selectable` scope, focus-ring tokens that work with negative `outline-offset`, `portalProps.to` scoped to the Settings subtree, decorative motion gated on the optimized-mode flag, and verification in a real frameless window on macOS *and* Windows.

The four documents agree on the decisive points. Where they differ, the conflict is stated and resolved below — these are the decisions a planner must not re-litigate.

## Implications for Roadmap

Based on the combined research, seven phases. Phase 1 gates everything; Phase 2 carries the highest severity; Phase 3 is reordered ahead of the surface revamp per C6.

### Phase 1: Toolchain Gate — Svelte 5 (Legacy Mode) + Vite 7 + TypeScript 5.9
**Rationale:** Svelte 5 cannot be installed alone — Vite, the plugin, TS, `svelte-check`, ESLint's Svelte plugin, the tsconfig base, and Vitest are mutually pinned and must move as one unit. This is the **highest-uncertainty** phase and the only one that touches the shared build, so it warrants its own phase with its own verification. **No syntax migration:** every component keeps `export let`, `on:`, `$:`, slots.

### Phase Ordering Rationale

- **Phase 1 first because it gates everything and nothing else can be verified until the build is green.** It also carries the phase most likely to *go wrong*, and it is the only phase that touches the shared build inputs (`preBuild.js`/`postBuild.js`/`cleanBuilds.js` all hold literal strings that move).
- **Phase 2 second because it carries the highest *severity*.** It is the only phase that can silently degrade a live service, and it is the only phase whose acceptance test is "nothing changed." Doing it before any component exists is what makes that test meaningful.
- **`design/tokens.ts` runs ahead of Phase 2** (pure, framework-free, unit-testable, unblocked by Phase 1) — this de-risks the critical path by forcing the token-role decisions to be settled before they are expensive.
- **Phase 3 before Phase 5** so the revamp walks the final IA. The id migration is the risky part; isolating it in its own phase with a redirect table — rather than folding it into a styling pass — is the mitigation.
- **Phase 4 before Phase 5** because the primitives are the leverage point: nine rebuilt wrappers upgrade twenty-one tabs, and Bits UI is what makes the accessibility goal affordable at all.
- **Grouping rationale:** Phases 1–2 are *foundation* (no UI change, both with output-neutral acceptance tests); Phases 3–5 are *the surface* (structure, then layer, then migration); Phases 6–7 are *quality and proof* (verify, then document). Each phase is independently shippable, and the reversibility ladder means any phase can be backed out without data migration — themes are never rewritten.
- **How this avoids pitfalls:** the shared-bundle hazard is contained by Phases 2 and 6's gates; the token collision is contained by Phase 2's contract document; the toolchain churn is contained by Phase 1's isolation; the event/prop boundary churn is contained by Phase 4's tests-before-conversion rule; the "two theming systems" failure is contained by revamping the Theme tab inside Phase 5 rather than deferring it.

### Gaps to Address

Each gap has a named owner phase and a concrete resolution. None is a blocker.

1. **`@theme inline` may emit a `:root` block, which PROJECT.md forbids.** shadcn's token setup pairs hand-written `:root`/`.dark` blocks with `@theme inline`. Even if the hand-written block is correctly re-scoped to `[data-ds="v2"]` (per C4), Tailwind's own theme emission may still write variables to `:root` — and that CSS is in the bundle every window loads. *Resolve in Phase 2:* inspect the built CSS, confirm what lands on `:root`, and verify the emitted variables are new names that change nothing in an output window. This is the single most important item to verify before Phase 4.
2. **Legacy↔runes interop boundary.** `bind:` will not work against shadcn components (they do not declare `$bindable`); `on:click` is not how Bits UI communicates; composition uses snippets, not slots. *Resolve in Phase 1/4:* one throwaway component pair, documented, before the Settings rewrite starts.
3. **Icon-system fork (unresolved — see C9).** Lucide inside primitives vs. mapping onto the existing `Icon.svelte`/`values/icons.ts`. *Resolve in Phase 4* with a written decision; the recommended default is Lucide inside `components/ui/**` only, with a published mapping table.
4. **Bundle-size budget is unquantified.** The renderer is a single IIFE bundle with no code splitting, loaded by every output window — so every byte reaches the live-presentation path. *Resolve in Phase 2:* establish a `bundle.js`/`bundle.css` baseline and a per-phase budget; track the delta as an acceptance metric in Phases 4 and 5, and consider code-splitting Settings behind a dynamic import if the delta proves material.
5. **Whether any output-window code path renders Settings-adjacent UI.** The milestone scopes `Output.svelte` out, but the bundle is shared. *Resolve in Phase 2:* verify, do not assume.
6. **`eslint-plugin-svelte@3` with ESLint 8 eslintrc.** STACK.md rates this MEDIUM: the plugin is flat-config-first, and keeping ESLint 8 avoids a flat-config rewrite only if the eslintrc shim works. *Resolve in Phase 1:* verify `config/linting/eslint.svelte.js`, or budget the flat-config migration as its own task.
7. **ESLint regression risk.** The plugin swap is not optional, and the repo's `@typescript-eslint` rules that are currently *off* must stay off — the upgrade must not become a typing cleanup. Keeping `strict: false` and ~2,733 `any` uses is explicitly fine.
8. **Contrast verification across all 13 built-in themes.** The dark theme plus the pink `--secondary` accent frequently sit below threshold, and user themes vary further. *Resolve in Phase 6* with an automated audit against `defaultThemes.ts` plus user themes — not a spot check.
9. **Stylelint vs. Tailwind at-rules.** `stylelint-use-logical` and `stylelint-config-html` will fight `@theme`, `@custom-variant`, `@apply`, and `@source`; generated shadcn files will also need ignoring. *Resolve in Phase 2:* an explicit allow/ignore pass, keeping logical-property enforcement on hand-written component styles (RTL matters — `dir` is set at runtime).
10. **Prettier `printWidth: 500` vs. vendored shadcn files.** `shadcn-svelte add` output will not match the project's config, and reformatting produces a large diff per component. *Resolve in Phase 4:* decide reformat-on-add (recommended) and expect the diff.
11. **Security items carried from PITFALLS, not yet scheduled.** Validate theme colour values before `setProperty` (an imported theme file can inject arbitrary CSS variable values); never mount the DS into weak-isolation windows (`loadingOptions`, `screenIdentifyOptions`, `exportOptions`, `WebRtcHost` — `contextIsolation: false`); route any HTML-rendering primitive through a sanitizer at the DS boundary; note that shadcn dialogs/popovers rely on inline styles, which works only because no `style-src` is currently declared. *Assign to Phase 4/5* with explicit acceptance checks (`security_enforcement: true` is on in the project config).
12. **Vite 8 / Rolldown is the long-term target and must not be forgotten.** *Schedule as a separate, isolated post-milestone upgrade* once Settings has shipped and the IIFE lib output has been validated against Rolldown in a spike.
13. **Two decisions already resolved by the research, recorded so they are not re-opened:** do not adopt `svelte-sonner` (use the existing `newToast()`); do not adopt a binary `.dark` toggle or `mode-watcher`.
